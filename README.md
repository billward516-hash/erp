# Integrated Business Operating Platform

A cloud ERP/CMMS/LMS platform for small and midsize manufacturers, built as a TypeScript modular monolith on PostgreSQL. `docs/BRIEF.md` is the master scope. This repository currently contains the **Phase 0 foundation and the first vertical slice**:

- **Multi-tenant security**: tenant → legal entity → facility hierarchy, isolation enforced by PostgreSQL row-level security, facility-scoped RBAC with corporate (consolidated) roles, and a tamper-evident hash-chained audit log.
- **Asset registry**: equipment, component hierarchy, functional locations, state history, and utilization/availability with honest data-coverage handling.
- **Controlled technical documents**: versioning, approval with separation of duties for safety-critical documents, immutable released versions, links to assets and work orders, search, and restricted access.
- **Corrective maintenance**: request → work order → technician assignment → pinned procedure version → labor and parts (planned vs actual, substitutions) → independent verification with return to service → close.
- **Internal LMS and qualifications**: courses mix video, classroom, self-study, on-the-job shadowing, graded quizzes and observed practical evaluations. Completion, a passed assessment, verified competency, authorization and a certificate are recorded as separate states. Work orders refuse technicians who lack a current qualification for the equipment. A procedure revision opens a training review instead of silently reassigning training.
- **Management of change**: change requests are screened into a risk level and review route, signed off through a shared approval engine (staged, role-based, no self-approval, re-approval after material changes), and implemented through an action plan the platform verifies against document, training and work-order records. Includes pre-startup safety review, temporary changes with expiry, and a change register.
- **Preventive maintenance and storerooms**: calendar and meter-based PM plans that generate work orders without duplicates and move forward when the work is verified. Storerooms with an append-only stock ledger: receipts, issues and returns on work orders, transfers, adjustments and cycle counts. Includes PM compliance and parts-to-reorder reports.
- **Purchasing**: suppliers and price lists, purchase requests approved by amount and spend type through the shared approval engine (with delegation and re-approval after changes), purchase orders capped at the approved amount (+10%), printable POs, and receiving into storerooms. Work orders and the reorder report draft requests for what is missing.
- **Accounts payable and accounting sync**: supplier invoices captured from the order (with the scanned file), checked against what was received, approved by a second person, and aged by due date. Approved bills go to the accounting system through an outbox with idempotent, retried delivery and a reconciliation queue; payment status comes back. Today's connectors: a generic CSV export and a clearly labeled MOCK accounting system. The QuickBooks Online / Xero connector waits on the pilot's choice.
- **Time and payroll export**: weekly timesheets where work-order hours appear automatically, supervisor approval with locking, overtime flagged for review, and a payroll-ready CSV with the provider's earning codes. A time and labor report includes wrench time.
- **Notifications**: approvers are told when something reaches their stage, requesters when it is decided, technicians when work is assigned or parts arrive. A daily sweep reminds people about PM, overdue work, training, expiring qualifications, late orders, invoices and timesheets. Each person can mute kinds and opt into a daily email digest (development mail adapter only so far).
- **CRM and sales**: customers and contacts, an opportunity pipeline, activities and follow-up reminders. Quotes get pricing approval when the discount or margin is outside limits, keep the exact PDF sent for each revision, and become sales orders on acceptance. Orders ship from storerooms.
- **Receivables**: invoices drafted from what shipped, numbered and stored as PDF when issued, and sent to accounting through the same outbox as bills. Payments are applied to invoices (or come back from accounting). Orders that take a customer over their credit limit are held until finance releases them. A collections queue, call log with promises to pay, payment reminder emails, and an AR aging report with days sales outstanding.
- **Production**: work centers tied to machines, product revisions holding the bill of materials and routing (released revisions are frozen), and production orders that pin a revision. On the shop floor, operators start and stop runs on machines they are qualified to operate and record good, scrap (with a reason) and rework. Materials issue from storerooms; finished goods are received into stock. A production status report covers yield, scrap reasons, actual vs standard hours and machine throughput. Bills of materials import from flat or indented exports.
- **Quality and safety**: nonconformances raised from production scrap, receiving, customers or internal finds, with containment, disposition (concessions need a justification and a second person) and cost. Corrective actions run from root cause through actions to an effectiveness check that the owner cannot sign. Anyone can report incidents and near misses; injury details are visible only to the safety team. A shared action tracker sends reminders. Instruments under calibration control block production when overdue, and a calibration found out of tolerance raises a nonconformance listing the runs measured with it since its last good calibration. Internal audits record evidence per checklist item, and every finding must be answered before close. FMEAs (process, design, equipment) compute AIAG-VDA action priority (or RPN), require actions on high-priority failure modes, go through quality review, record risk after actions, and compare equipment failure modes with real work-order history. Business continuity plans give each critical process an RTO, dependencies checked against live records (machines down, too few qualified people, sole-source suppliers), recovery steps per scenario and a call list; exercises prove (or fail to prove) recovery within the RTO, and findings become actions. Photos and certificates attach to records. Equipment reliability shows failures, MTBF and MTTR per machine against the previous period, with bad actors and repeat failure codes, from the same state history as availability. Reports cover cost of poor quality, repeat parts and suppliers, recordable cases and the incident rate from timesheet hours.
- **Maintenance materials**: spare parts lists per machine with critical minimums (imported from OEM lists), repair templates (repair BOM plus labor estimate) applied to work orders, and kits for work orders. PM work orders get a kit automatically. Stock is reserved in the storeroom (virtual kit) or staged on a kit shelf (physical kit), issued to the job, and unused parts are returned. A kit-readiness report shows upcoming work that is short of parts.
- **Customer data onboarding**: CSV/XLSX/JSON in any reasonable shape. Auto-mapping and saved declarative profiles feed a dry-run staging step, then commit. See [`docs/DATA_ONBOARDING.md`](docs/DATA_ONBOARDING.md).
- **Reporting service**: one computed result rendered as JSON, CSV, print HTML and PDF, with answer-first headlines.
- **Sample data**: two fictional companies, loaded through the import pipeline from deliberately messy sample files.

- **Offline for technicians**: installable app; my work orders readable without a connection; labor, parts used and status changes queued on the device and sent when back online, exactly once (idempotency keys).
- **Shift passdown**: a shift log with facts compiled from the records (machines down, urgent work, output and scrap, quality and safety events), the writer's notes and items that carry over until resolved, handed over and acknowledged by the next shift.
- **SPC** (brief §12.7): characteristics on a part, operation, machine and gauge; X̄–R and individuals charts with limits set from a baseline; the four common run rules; signals that alert quality and are answered with a cause, optionally raising a nonconformance; Cp/Cpk/Pp/Ppk with the assumptions stated; measurements refused when the gauge was out of calibration and flagged when it is later found out of tolerance; CMM and gauge exports imported in their own layout.
- **Planning** (brief §12.8, first slice): customer forecasts imported in the customer's layout, versioned and reviewed against the previous version and firm orders; a deterministic plan that turns forecasts and firm orders into work-center load against demonstrated capacity (calendar × machines × measured availability, demonstrated run rates and yields) and into material needs with order-by dates; every assumption listed; scenarios such as a second shift or a forecast change compared with the plan as is; one click drafts the purchase request for the shortfall or creates planned production orders, and preventive maintenance comes off capacity.
- **Landlords and retail chains** (docs/FIT_PROPERTY_RETAIL.md): properties and stores as sites, grouped into portfolios, regions or districts, with managers granted a whole group. Units, suites and common areas are spaces that get work orders and QR codes. Residents and store staff report problems through a per-site link without signing in, into a request inbox. Work goes to contractors with a not-to-exceed amount, after a check that their certificate of insurance is current; their invoices are held to that limit. Response and completion targets per priority, with a report by site or contractor. Leasing: rental units, leases with renters as customers, notice, move-out and renewal, monthly rent billed through receivables with day proration, a rent roll with occupancy, vacancy loss and past-due rent, and unit turns whose make-ready jobs are work orders. Sample landlord tenant (Harborview) imported from property-management exports, rent roll included. Store operations: cooler and freezer logs with limits (an out-of-limit reading raises one maintenance request per excursion; missed readings are reminded), monthly store walks on checklists with scores, repeats and follow-up, and a store standards report. Sample retail tenant (Northwind Market, five stores in two districts).
- **Web app** (React): home dashboard, assets with QR deep links, technician work-order execution, approvals inbox, change requests with screening and pre-startup review, training with quizzes and evaluator sign-off, PM schedule and plans, storerooms (stock, ledger, receiving, cycle counts), purchasing (requests, orders, suppliers, receiving, delegation), payables (invoice capture, approval, payment status), accounting connection (sync queue, file downloads, account mapping), timesheets (my week, team approvals, payroll export), production (orders, shop floor, products and routings, work centers), quality (nonconformances, corrective actions, FMEA, calibration, audits, my actions), safety (report, incidents), business continuity (plans, gaps, exercises), customers and pipeline, quotes and orders, receivables (invoices, collections, payments, credit hold), reports with CSV/PDF export, and the data import wizard. Works at phone width.

Not built yet: production SSO, a QuickBooks Online / Xero connector (waits on the pilot's system), a payroll-provider connector (waits on the pilot's provider), credit memos and customer returns, MRP and scheduling. See [`docs/ROADMAP.md`](docs/ROADMAP.md).

## Quick start

Requires Node 22+ and PostgreSQL 16 binaries. `scripts/dev-db.sh` starts a local cluster on port 54329 without Docker.

```bash
npm install
npm run db:start      # local PostgreSQL cluster in ./.pgdata (databases erp, erp_test)
npm run seed          # RESETS the dev db, migrates, loads sample tenants, prints API tokens
npm run web:build && npm start   # API + web app on http://localhost:3000 (sign in with a dev token)
# or, while developing: `npm run dev` (API :3000) and `npm run web:dev` (UI :5173 with hot reload)
npm test              # typecheck with `npm run typecheck`; tests run against erp_test
npm run ui:smoke      # drives the built UI as several demo users (needs a freshly seeded running server; BASE_URL)
npx tsx scripts/run-sync.ts        # one accounting sync for every tenant with a connection (schedule it, e.g. every 5 min)
npx tsx scripts/run-reminders.ts   # daily reminders + email digest (development mail adapter: .storage/mail/*.eml)
```

`npm run seed` writes dev tokens to `.storage/dev-tokens.json`.
