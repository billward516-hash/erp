There are two separate safety nets, and it matters which one you reach for. Company archives are taken by the system itself and are for undoing mistakes inside one company: a record deleted by accident, a bad import that overwrote prices. Database backups are taken by whoever runs the server and are for disasters: a lost disk, a failed upgrade. This page covers both, but the archive screens are the part you use.

Only an administrator sees Admin → Archives and restore. Rolling the whole company back needs two administrators.

Company archives

An archive is a full copy of the company's data from one consistent moment, saved as a compressed file with a checksum. The daily job takes one whenever the last is older than the interval, every 30 days by default, and keeps the latest 12 scheduled ones. The very first is taken by the first daily run after the company is set up.

What an archive holds: every business record the company owns (work orders, stock movements, invoices, documents' records and so on), as database rows. What it does not hold: sign-in tokens, single sign-on secrets, people's unsaved form drafts, and the archives themselves. It holds the rows that refer to uploaded files, but not the file contents; those live in the server's storage folder and are protected by the server operator's file backups.

Archives are stored in the same storage folder as uploaded files. If that folder is lost and not backed up, the archives go with it. That is why they do not replace database backups.

The page

The sentence at the top says how long ago the last archive was taken and when the next is due. The table lists each archive with when it was taken, its kind (Scheduled, Taken by hand or Before a rollback), the number of records, size and who took it. Actions per row: Bring records back, Download (a compressed file) and Roll back to this.

Take an archive now

Choose Archive now. Do this before any big import, bulk change or go-live cutover. On a test company with two years of history (about 20,000 ledger lines, 17.9 MB archive) it took about five seconds.

Change the schedule

  1. Choose the button that says Schedule: every 30 days, keep 12 (it shows your current values).
  2. Set Archive every (days) (1 to 90) and Scheduled archives kept (1 to 120). Choose Save.

Only scheduled archives are pruned. Archives taken by hand and the ones taken automatically before a rollback are kept until removed by the operator.

Bring a record back

Use this when a record was deleted or changed and you need the old version. Nothing else changes.

  1. On Archives and restore, choose Bring records back on the archive taken before the mistake.
  2. Under Kind of record pick the kind (each shows how many were archived). Optionally type a number, name or any text in Find and choose Search.
  3. The page says how many were deleted and changed since the archive, and shows up to 50 rows, deleted ones first. The column Since the archive shows Unchanged, Changed or Deleted. Tick the ones to bring back.
  4. Leave Include the records that belong to them (lines, steps, contacts) ticked unless you only want the top record. Choose Bring back N.

Records are written back exactly as they were, with every business rule and reference still checked. If a record points at something that no longer exists, the restore is refused with a message, and nothing is half-restored. You can bring back at most 500 records at once. The result is recorded in the audit trail.

Roll the whole company back

This replaces everything entered since the archive. Use it only soon after a large mistake, such as a bulk import into the wrong place, and only if bringing records back would be too slow.

What it keeps

People, roles and their assignments, sign-in settings and tokens, the audit trail, record number counters (so numbers are never reused), the licence, and people's drafts are kept as they are now. Business records are replaced by the archive's. References left pointing at something that no longer exists are cleared. If the archive itself turns out to be inconsistent, nothing changes.

Steps

  1. Administrator A chooses Roll back to this on the archive, types Why (at least five characters, for example “A bad import overwrote prices”) and chooses Ask a second administrator to confirm. The button is disabled, with an explanation, if the company has only one administrator: add another first.
  2. All administrators are notified. A banner, Rollback waiting for a second administrator, appears on the page.
  3. Administrator B reads the reason and chooses Confirm the rollback. Administrator A cannot confirm their own request, and either can Cancel it. A request not confirmed within 24 hours expires.
  4. The system first archives the present state (kind Before a rollback), then replaces the business data in one step. The result is shown under Rollbacks: how many records were restored. On a test company with two years of history it took about 25 seconds.

To undo a rollback, roll back again to the Before a rollback archive. Only one request can wait at a time.

If the page says “this database does not let the platform suspend reference checks during a rollback; ask the platform operator to run it” (error rollback_unavailable), your hosting database does not give the platform the privilege the rollback needs. Ask the server operator; nothing was changed. Also, work done by other people between the request and the confirmation is lost; tell them before you confirm.

Database backups and the drill

These are run by the server operator; the table shows what to ask for. Full detail is in Security and operations.

  • Database: the hosting provider's point-in-time recovery, or a nightly pg_dump plus a roles dump.
  • Files: snapshot the storage folder at the same time. A restored database with older files (or the reverse) shows missing attachments, not corruption.
  • The sign-in secret key (SSO_SECRET_KEY) kept separately in a secret store; losing it means retyping identity-provider secrets.

The backup drill

A backup nobody has restored is only a hope. The drill (npx tsx scripts/backup-drill.ts, also npm run backup:drill) dumps the database, restores it into a scratch database, and checks that the same migrations are present, every table has the same number of rows, every company's audit chain still verifies, and row-level security still blocks access without a company. The time it takes is your recovery-time evidence. Ask for it quarterly against a restored production snapshot, and keep each report.
