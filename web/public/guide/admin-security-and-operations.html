    Administrator brief

    Security and operations

    A plain-language runbook for the person who hosts the system: how it is deployed, its settings, upgrades, monitoring, backups, security posture, measured capacity and what is not done.

    Administrator brief: more technical, written for the person who sets the system up.

    This page is for whoever installs, hosts and keeps the system running. It restates the operations runbook in readable form. Where the product has not settled something (hosting provider, mail service, identity provider), it says so rather than assuming. If you are the company administrator and someone else hosts the system, read it so you know what to ask them for.

    The shape of a deployment

    • One Node 22 program (started with npm start) that serves both the API and the web application. Build the web application first with npm run web:build.
    • PostgreSQL 16 with two database logins. The owner login (DATABASE_ADMIN_URL) runs migrations and the daily jobs that must cross companies. The application login (DATABASE_URL) is the one every request uses, and it is restricted by row-level security (RLS): the database itself refuses to show one company's rows to another, whatever the program does. The two logins must be different.
    • A persistent folder for uploaded files and company archives (STORAGE_DIR). There is no cloud object-storage option yet, so the folder must be on a persistent disk and be backed up together with the database.
    • A reverse proxy or load balancer that provides https in front, with TRUST_PROXY=1.
    • Run a single copy of the program for now. The rate limiter keeps its counts in memory. The daily job is safe with several copies (the first to claim the day does the work), but limits would then be per copy. Restarting is safe at any time.

    Configuration

    Settings are environment variables. When NODE_ENV=production the server refuses to start if a required one is missing or unsafe, and logs a warning for the others.

    VariableRequiredWhat it is
    DATABASE_URLYesThe application login. Must not be the owner login and must not use a development password.
    DATABASE_ADMIN_URLYesThe owner login.
    APP_BASE_URLYesThe public https:// address. Used in links in emails and as the base of the single sign-on redirect address.
    SSO_SECRET_KEYYesEncrypts the identity-provider client secrets stored in the database. At least 32 characters is checked at start; in use the program needs it to be 32 random bytes written in base64, so generate it with openssl rand -base64 32. Keep a copy in your secret store, separate from the database backup: losing it means retyping every company's identity-provider secret.
    STORAGE_DIRWarnedThe persistent folder. Default ./.storage is lost when a container is replaced.
    TRUST_PROXYWarned1 behind one proxy, so rate limits see real client addresses.
    METRICS_TOKENWarnedTurns on /metrics (404 otherwise) for a scraper presenting this token.
    SMTP_HOSTWarnedThe outgoing mail server. If it is not set, email is not delivered: digests are written as files under STORAGE_DIR/mail and a warning is logged at start. Set it to send real email.
    SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_SECURENoPort (587; 465 with TLS), login (set both user and password or neither), and encryption: starttls (default; the connection must become encrypted before login), true (encrypted from the first byte) or false (none; only for a trusted relay on the same machine, and warned). The password is never logged, stored or shown.
    MAIL_FROMWarnedThe sender address on emails, for example Ops Platform <notifications@your-domain>. The domain needs SPF, DKIM and DMARC records set up with your mail provider.
    PORT, LOG_LEVELNoListening port (3000), log level (info).
    MAX_UPLOAD_BYTESNoLargest upload; default 50 MB.
    RATE_LIMIT_PER_USER, RATE_LIMIT_PER_ADDRESSNoRequests per minute: 1200 per signed-in user, 120 per address for sign-in and public pages. 0 turns one off.
    DAILY_JOB_ENABLED, DAILY_JOB_HOUR_UTCNoThe built-in daily scheduler, on by default at 06:00 UTC. See Scheduled jobs.

    First deployment

    1. Create the two database logins and an empty database. The logins must exist before the migrations run, because the migrations grant rights to them. scripts/dev-db.sh shows the development equivalent.
    2. Install and build: npm ci, then npm run web:build.
    3. With DATABASE_ADMIN_URL set, run npm run db:migrate. Migrations only move forward and are recorded in a table called schema_migration.
    4. Start the server. Check GET /health (the program is up) and GET /ready (the database answers and every migration of this build is applied; it answers 503 otherwise).
    5. Create the first company and administrator with npx tsx scripts/create-company.ts --slug <slug> --name "<name>" --admin-email <email> (it needs DATABASE_ADMIN_URL; add --edition lite for Lite, --help for every option). It wraps provisionTenant, adds the administrator and prints that person's first token once; the token expires after 14 days unless you choose otherwise. There is deliberately no customer-facing screen for creating a company. A company is created as Standard or Lite, with its first site. Field service and later edition changes are switched with scripts/set-entitlement.ts (see Features and editions).
    6. Sign in with that administrator's token and continue with Your first week.

    Upgrading

    1. Take a backup (see below). Also choose Archive now for each company if you can.
    2. Deploy the new build, run npm run db:migrate, restart. Until every migration has applied, /ready answers 503, so a load balancer holds traffic away from a half-upgraded copy.
    3. Rolling the program back is safe only while no new migration has been applied. Migrations cannot be reversed; after one has run, the way back is to restore the backup.

    Backup and recovery

    • Database: the hosting provider's point-in-time recovery if it is managed; otherwise a nightly pg_dump (custom format) plus pg_dumpall --roles-only.
    • Files: a snapshot of STORAGE_DIR taken at the same time. A restored database with older files (or the reverse) shows missing attachments, not corruption. Company archives are stored in the same folder.
    • The secret: SSO_SECRET_KEY in the secret store.
    • Drill: npx tsx scripts/backup-drill.ts (or npm run backup:drill) dumps the database, restores it into a scratch database and checks migrations, row counts for every table, every company's audit chain, and that row-level security still blocks access without a company. The restore time it reports is your recovery-time evidence. Run it against a restored production snapshot at least quarterly and keep the report.
    • Per company: the system's own archives (every 30 days) let an administrator bring back one record or roll a company back; use that for “undo a bad import”, not for disaster recovery. See Archives and recovery.

    Monitoring

    • /health and /ready for probes. Alert if /ready fails for more than a minute. A 503 body says either that migrations are not applied (and lists them) or that the database is unavailable.
    • /metrics (Prometheus text format, needs Authorization: Bearer <METRICS_TOKEN>) shows request counts and latency histograms by route and status, and rate-limit refusals. Alert on the share of 5xx responses and on slow (p95) latency.
    • Logs are JSON, one line per request, with a request id that is also returned to the browser in x-request-id. Credentials are removed. An unexpected error shows the user “internal error (reference <id>)”; search the logs for that id.
    • The daily job: check Admin → Scheduled jobs. A day without a run means the scheduler did not run.
    • The audit trail is a hash chain: each event includes a fingerprint of the one before, so later tampering shows. It is verified by the backup drill and the system check, and on request by anyone with the audit.view permission.

    Rate limits and error codes you will see

    • Every signed-in user: 1200 requests a minute. Sign-in pages and public request forms: 120 a minute per address, with separate budgets so a shop full of staff using one public link does not block sign-in.
    • An address that keeps sending wrong tokens is refused before its tokens are even looked up.
    • Over the limit gives status 429, code rate_limited, “Too many requests. Try again in N seconds.”, with a Retry-After header. If whole offices are blocked, check TRUST_PROXY.

    Security posture

    • Company isolation is enforced in the database by row-level security and tested: 218 tables checked in both directions with no leaks in the last system check.
    • Every database statement is parameterised; the few that build text do so only from fixed column names or quoted catalogue names.
    • Uploaded files are never shown as active content: HTML, SVG and scripts are forced to download with a restrictive policy.
    • CSV and Excel exports neutralise cells that could run as formulas.
    • Security headers on every response (content security policy, no framing, no content sniffing, strict transport security on https).
    • Production settings are checked at start; secrets are encrypted at rest; tokens are stored only as fingerprints; single sign-on uses PKCE and verifies the signature, issuer, audience, expiry and nonce of the ID token.
    • The identity-provider address a company administrator types is fetched by the server. It is not outside input, but a hosted deployment with many companies should still limit outbound traffic from the app host to approved destinations.
    • Known advisories: npm audit --omit=dev reports four entries (react-router and its wrapper; uuid and the Excel library that uses it). Both were assessed as not reachable in this application; fixing the first needs a major upgrade that is planned.

    Capacity: measured, not promised

    Measured with scripts/load-test.ts on a company with two years of generated history (about 20,000 ledger lines and 17,500 audit events), one program copy and one local database on the same small development container, with a mix of list, detail, search, book and report reads and 5% work-order creation.

    ScenarioRequestsThroughputp50p95p995xx
    50 users, short pauses, 60 s8,246131 /s23 ms289 ms472 ms0
    100 users, no pauses, 45 s9,082186 /s418 ms928 ms1,249 ms0

    Read this as: one copy serves a few dozen simultaneously active users comfortably at this data size. It does not cover many companies in one database, very large uploads, or your real network and hardware. Re-run the test on the real environment before go-live. The test data are generated, not recorded, so their patterns are plausible rather than calibrated.

    The one known slow report is Repair or replace: it evaluates assets one at a time (under a second on the 160-machine test company, a few seconds under load). A company with thousands of assets that opens it often would need it rewritten as a single query. Lists return up to 200 rows, so keep screens paged.

    Routine tasks

    WhenTask
    Daily (automatic)Reminders, expiry alerts, approval nudges, archives due, retention.
    WeeklyCheck backups completed; glance at 5xx and rate-limit counts; check the Scheduled jobs page shows the daily run as Done, including the accounting sync and email steps.
    QuarterlyBackup drill on a restored snapshot; review users and roles; review API tokens.
    Each releaseThe upgrade steps above; npm test, npm run typecheck and the smoke and accessibility scripts.

    What is not done

    • Independent penetration test. Not yet done; the self-review above does not replace one.
    • Email delivery against a real provider. The server can send through any SMTP service, but this has been verified only against a stand-in mail server in the tests. No real provider or sending domain has been connected or tested (owner item O-2). Until you set SMTP_HOST nothing is delivered; after you do, press Send a test email to me on the Scheduled jobs page and check the message arrives and is not filed as spam.
    • Hosting choice, container image and deployment files. Deliberately not included until the hosting is chosen.
    • Cloud object storage for files and archives.
    • More than one program copy (limits are in memory).
    • A more frequent accounting sync. It runs once a day inside the daily job; for more often, schedule scripts/run-sync.ts or press Sync now.
    • A customer-facing screen for creating a company or switching the licence. Deliberately not built: the operator uses scripts/create-company.ts and scripts/set-entitlement.ts.
    • Live connections to bank feeds, payroll providers and accounting software (files only).

    Decisions still open for the owner: hosting, the outgoing email provider and sending domain, the identity provider, the first pilot customer and the penetration-test vendor.
