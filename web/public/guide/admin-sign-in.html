    Administrator brief

    Sign-in and access tokens

    Set up single sign-on through your identity provider, understand how people are matched to accounts, and manage API tokens.

    Administrator brief: more technical, written for the person who sets the system up.

    On this page
    • What to give the identity provider
    • Set it up
    • How people are matched to accounts
    • API tokens
    • Problems you may meet

    People sign in through the company's own identity provider using OpenID Connect (OIDC), the standard behind “Sign in with Microsoft” and “Sign in with Google”. It works with Microsoft Entra ID, Google Workspace, Okta, Auth0, Keycloak and any provider that publishes a discovery document. The platform keeps no passwords. The other way in is an API token, meant for scripts and for the first administrator before single sign-on is set up.

    Only an administrator sees Admin → Sign-in. Setting it up usually needs a second person who administers the identity provider.

    What to give the identity provider

    Ask the provider's administrator to register a new web application (a “confidential client”) with these settings.

    SettingValue
    Redirect URI (sign-in redirect URL, reply URL)Shown on the page as Redirect URL. It is your public address followed by /auth/sso/callback, for example https://erp.example.com/auth/sso/callback. It comes from the server's APP_BASE_URL setting, so check it is right before you hand it over.
    FlowAuthorization code, with PKCE (the system always sends a PKCE challenge).
    Scopesopenid email profile
    Client authenticationA client secret, sent to the provider with HTTP Basic authentication. A client with no secret also works (the secret field may stay empty).
    ID token signatureRS256 or ES256. Tokens signed any other way are refused.

    In return you need three things: the issuer address (for Microsoft Entra ID it looks like https://login.microsoftonline.com/<tenant id>/v2.0), the client id, and the client secret.

    Claims the system reads

    ClaimUsed for
    subThe person's permanent identity at the provider. Required. After the first sign-in the account is tied to the pair (issuer, sub).
    emailFinding the user on the first sign-in.
    email_verifiedMust be true for the first sign-in to link by email. Some providers do not send it unless you ask for it as an optional claim; if people see “the provider did not confirm the email address”, this is the cause.
    iss, aud, exp, iat, nonceChecked for you: the issuer must match, the token must be for this client id, must not be expired (one minute of clock drift is allowed) and must belong to this sign-in attempt.

    The name claim is not used; names come from your people import.

    Set it up

    1. Open Admin → Sign-in (the page title is Sign-in).
    2. Copy the Redirect URL to the provider's administrator and wait for the issuer, client id and secret.
    3. Enter the Issuer (it must start with https://; a trailing slash is removed), Client id and Client secret.
    4. In Work-email domains enter the domains your staff use, separated by commas, for example example.com, example.co.uk.
    5. Leave Link a person's first sign-in by their verified email ticked (see below).
    6. Tick Single sign-on is on and choose Save. When it is on, the system fetches the provider's discovery document to check it can be reached. If it cannot, you get an error and nothing is turned on.
    7. Sign out and sign in as a person: on the Sign in page type your work email and choose Continue with your company account.

    The secret is write-only. After saving, the field shows “Saved (leave blank to keep)”. It is stored encrypted with the server's SSO_SECRET_KEY; if that key is lost, you must enter the secret again.

    To rehearse before you have a real provider, the server operator can run a test provider with npm run mock-idp. It is only for trials.

    How people are matched to accounts

    1. Finding the company. The person types an email. The system looks at the part after the @ and finds the company whose Work-email domains contain it. A domain can belong to only one company; saving a domain another company already uses fails. (A direct link can also name the company.)
    2. Signing in at the provider. The person is sent to the provider, signs in there, and comes back.
    3. Finding the user. If the identity (issuer and sub) is already linked to an active user, that user is signed in. Otherwise, if the email is verified and the option is ticked, the system looks for an active user with that email that has never been linked, links it, and signs in. Otherwise the person sees “<email> is not a user of <company>; ask your administrator to add you”.

    Things the rules imply:

    • Nobody is created by signing in. Add people first, one at a time under Admin → People and access or in bulk with the People who sign in, with roles import (Sites and people).
    • The domain list only decides which company to send the person to. It does not restrict who may sign in. What decides access is an active user with a matching verified email, or an already linked identity.
    • If you untick Link a person's first sign-in…, nobody who is not already linked can sign in for the first time. Leave it ticked unless you have a specific reason.
    • Each user can be linked to one identity only. If you change to a different issuer, people linked to the old one cannot be matched again by email while they are still linked. Before changing provider, open each person under Admin → People and access and choose Unlink (see Single sign-on identity), then change the provider here. At their next sign-in they are matched by verified email and linked to the new identity, provided Link a person's first sign-in… is ticked. If the new provider reports a different email, add the identity by hand with Link identity.
    • Single sign-on gives a session that lasts 12 hours. Signing out ends it at once.

    API tokens

    An API token is a long code beginning erp_ that stands in for a password. It lets a script, or a person at the development sign-in fold-out, act as one user with that user's roles. Only a fingerprint of the token is stored, so a lost token cannot be shown again.

    • Administrators issue and revoke tokens under Admin → People and access → Tokens (see below). The first administrator's token is created on the server when the company is set up (scripts/create-company.ts); sign in with it, set up single sign-on, then revoke it. The practice copy has its own token (shown once; see Implementation planner).
    • Treat a token like a password: it carries all the roles of its user.
    • The tick box API tokens keep working (integrations and scripts) controls them. Unticked, tokens stop working for the company, but single sign-on sessions still do.
    • The system will not let you untick it unless you yourself have signed in with single sign-on at least once, so that you cannot lock yourself out (“sign in once with single sign-on yourself before turning API tokens off”).
    • Expired or revoked tokens are removed by the daily clean-up after a period you set under Admin → Data retention (default 30 days).

    Issue, check and revoke a token

    1. Open Admin → People and access → Tokens. Under Issue a token, choose the person it Acts as, say what it is for (for example Payroll export), choose when it expires (30 days, 90 days, a year, or never) and choose Issue token.
    2. The new token is shown once. Copy it now. Only a fingerprint (a one-way hash) is stored, so nobody, including the operator, can show it again. If it is lost, issue another and revoke the lost one.
    3. The list shows, for each token, who it acts as, who created it and when, Last used (to about the minute) and when it expires. Revoked and expired tokens are hidden until you tick Show revoked and expired.
    4. To revoke, choose Revoke and confirm. It stops working at once.

    A token can do everything the person it acts as can do, so it can only be issued by an administrator who holds all of that access too: a plant administrator cannot issue a token that acts as a company-wide administrator. Issue tokens to a dedicated user with only the roles the job needs (an “integration” user), not to a named employee. A disabled person cannot be given a token, and a disabled person's existing tokens do not work. Issuing and revoking are recorded in the audit trail with who, for whom, the label and the expiry, never the token.

    Rotating a token

    1. Issue a new token for the same person with the same label.
    2. Put the new token into the script or system that uses the old one.
    3. Check that the new token's Last used shows a recent time.
    4. Revoke the old token.

    Choose an expiry for every token that you can; set a reminder to rotate before it ends. A token with no expiry stays valid until someone revokes it.

    Leave API tokens on until at least two administrators have signed in through single sign-on. If single sign-on breaks (the provider is down, or the secret expired), a token is your way back in. Turn tokens off only when you have another recovery route agreed with the server operator.

    Problems you may meet

    MessageLikely cause and fix
    single sign-on is not set up for example.comThe domain is not in the list, or Single sign-on is on is not ticked. Add the domain and save.
    … is not a user of <company>; ask your administrator to add youNo active user with that email, or the provider did not confirm it. Add the person to the import; check email_verified.
    this sign-in has expired or was already used; start againThe sign-in took longer than 10 minutes, or the page was reloaded. Start again from the sign-in page.
    the provider says its issuer is "…", not "…"The issuer you typed differs from the one in the provider's discovery document. Some providers (Auth0, for example) report an address that ends with a slash while the system removes the slash from what you type; if the two cannot be made to agree, report it to the server operator.
    the ID token … (several variants)The token failed a check: signed with an unsupported algorithm, wrong client id, expired, or the server's clock is wrong by more than a minute. Check the client id and the server time.
    the identity provider answered 4xx / 5xxWrong client secret, wrong redirect URL registered, or the provider is unavailable. The provider's own error text follows.
